# 2. Filesystem Hierarchy Standard (FHS)

Linux distributions follow the **Filesystem Hierarchy Standard (FHS)**.

FHS defines:

* Directory names
* Their purposes
* What should be stored inside them

Because of FHS, most Linux distributions have nearly the same directory layout.

# Linux Special Permissions

## Overview

Linux provides three special permissions in addition to the standard read (r), write (w), and execute (x) permissions.

| Special Permission | Numeric Value | Symbolic | Applies To | Purpose |
|--------------------|--------------:|----------|------------|---------|
| SUID (Set User ID) | 4000 | u+s | Files | Program runs with the file owner's privileges. |
| SGID (Set Group ID) | 2000 | g+s | Files & Directories | Program runs with the file group's privileges (files) or new files inherit the directory's group (directories). |
| Sticky Bit | 1000 | +t | Directories | Prevents users from deleting or renaming files owned by other users. |

---

# 1. SUID (Set User ID)

## What is SUID?

Normally, a program runs with the permissions of the user executing it.

If SUID is set on an executable file, the program temporarily runs with the permissions of the file owner.

```
Normal Execution:

User ------> Program
Runs as: User

SUID Execution:

User ------> Program
Runs as: File Owner
```

---

## Why is SUID needed?

Some programs require root privileges even when executed by a normal user.

Example:

```bash
passwd
```

The `passwd` command updates:

```text
/etc/shadow
```

Only the root user can modify this file.

However, any user can change their own password because the `passwd` executable has the SUID bit set.

---

## View SUID

```bash
ls -l /usr/bin/passwd
```

Example output:

```text
-rwsr-xr-x
```

Notice:

```text
rws
```

instead of

```text
rwx
```

The **s** replaces the owner's execute permission.

---

## Set SUID

Symbolic:

```bash
chmod u+s filename
```

Numeric:

```bash
chmod 4755 filename
```

---

## Remove SUID

Symbolic:

```bash
chmod u-s filename
```

Numeric:

```bash
chmod 0755 filename
```

---

## Verify

```bash
ls -l filename
```

Example:

```text
-rwsr-xr-x
```

---

## Capital S vs Small s

Small s

```text
-rwsr-xr-x
```

Means:

- SUID is enabled.
- Execute permission exists.

Capital S

```text
-rwSr-xr-x
```

Means:

- SUID is enabled.
- Execute permission is NOT set.

Usually indicates a configuration mistake.

---

## Common SUID Programs

```text
/usr/bin/passwd
/usr/bin/su
/usr/bin/chsh
/usr/bin/chfn
```

---

## Find All SUID Files

```bash
find / -perm -4000 -type f 2>/dev/null
```

Explanation:

| Option | Meaning |
|---------|----------|
| / | Search entire filesystem |
| -perm -4000 | Search for SUID files |
| -type f | Only files |
| 2>/dev/null | Hide permission denied messages |

---

# 2. SGID (Set Group ID)

SGID behaves differently on files and directories.

---

# SGID on Files

## What is SGID?

When an executable has SGID enabled, it runs with the permissions of the file's group instead of the user's primary group.

```
Normal

User Group -----> Program

SGID

Program runs using File Group
```

---

## Set SGID

Symbolic:

```bash
chmod g+s filename
```

Numeric:

```bash
chmod 2755 filename
```

---

## Remove SGID

```bash
chmod g-s filename
```

---

## Verify

```bash
ls -l filename
```

Example:

```text
-rwxr-sr-x
```

Notice:

```text
r-s
```

---

# SGID on Directories

This is the most common use of SGID.

---

## Problem

Directory:

```text
/project
```

Group:

```text
developers
```

Two users:

```text
alice
bob
```

Without SGID:

Alice creates:

```text
report.txt
```

Group:

```text
alice
```

Bob creates:

```text
script.sh
```

Group:

```text
bob
```

Permissions become inconsistent.

---

## Solution

Enable SGID.

```bash
chmod g+s project
```

Now every new file automatically inherits the directory's group.

Result:

```text
report.txt -> developers

script.sh -> developers
```

Everyone in the developers group can collaborate.

---

## Verify

```bash
ls -ld project
```

Example:

```text
drwxrwsr-x
```

Notice the **s** in the group execute position.

---

## Capital S

```text
drwxrwSr-x
```

Means:

- SGID exists.
- Execute permission is missing.

Usually a mistake.

---

## Find All SGID Files

```bash
find / -perm -2000 -type f 2>/dev/null
```

# 3. Sticky Bit

Sticky Bit is used only on directories.

---

## Why?

Suppose a directory is writable by everyone.

Example:

```text

```

Permissions:

```text
777
```

Without Sticky Bit:

```
User A creates file

â†“

â†“

```

Anyone could delete anyone else's files.

---

## Sticky Bit Solution

When Sticky Bit is enabled:

Only one of the following can delete a file:

- File owner
- Directory owner
- Root

Everyone else is denied.




Means:

# Linux Inodes, Hard Links, and Symbolic Links

## Overview

In Linux, a filename is simply a human-readable pointer to a data structure called an **inode**. Understanding how inodes, hard links, and symbolic (soft) links work is fundamental for storage management, filesystem architecture, and system troubleshooting.

---

# 1. Inodes (Index Nodes)

An **inode** (index node) is a data structure on a filesystem that stores metadata about a file.

### What an Inode Stores:
- Inode number
- File type (regular file, directory, symbolic link, socket, etc.)
- Permissions (`rwx` for Owner, Group, Others)
- File ownership (UID and GID)
- File size (in bytes)
- Timestamps:
  - **atime**: Access time
  - **mtime**: Modification time (content change)
  - **ctime**: Change time (metadata/permission change)
- **Pointers to data blocks** on disk where actual content resides

### What an Inode Does NOT Store:
- **The Filename**: Filenames are stored separately inside directory files, mapping `filename -> inode number`.

### Useful Commands:
```bash
ls -li /etc/hosts     # -i displays the inode number
stat /etc/hosts       # displays full inode metadata and block information
```

---

# 2. Hard Links

A **hard link** is an additional directory entry (filename) pointing directly to an existing inode.

### Characteristics:
- Shares the **exact same inode number** as the target file.
- All hard links to an inode are **equal peers** (there is no "original" file).
- Deleting one hard link decrements the link count; data remains on disk until **all** hard links are removed (link count = 0).
- **Cannot span across different filesystems** (inodes are unique only within a specific filesystem).
- **Cannot be created for directories** (prevents filesystem loops/cycles).

### Usage & Syntax:
```bash
ln /path/to/target /path/to/hardlink

# Example
ln /var/data/app.conf /var/data/app.conf.bak
ls -li /var/data/app.conf*    # Output shows identical inode numbers and link count = 2
```

---

# 3. Symbolic Links (Soft Links / Symlinks)

A **symbolic link** is a special file containing a text string representing a path to another file or directory.

### Characteristics:
- Has its **own unique inode number**.
- Points to a **file path**, not directly to data blocks.
- **Can span across different filesystems**.
- **Can link to directories**.
- If the target file is deleted or moved, the symlink becomes **dangling/broken** (returns "No such file or directory" when accessed).

### Usage & Syntax:
```bash
ln -s /path/to/target /path/to/symlink

# Example: Link config to web app directory
ln -s /etc/nginx/nginx.conf /opt/webapp/nginx.conf
ls -la /opt/webapp/nginx.conf   # Output shows: nginx.conf -> /etc/nginx/nginx.conf
```

---

# 4. Side-by-Side Comparison

| Feature | Hard Link | Symbolic Link (Soft Link) |
| :--- | :--- | :--- |
| **Points to** | Inode Number | File / Directory Path String |
| **Inode Number** | Same as target | Unique (different from target) |
| **Target Deletion** | File data intact until all links deleted | Symlink breaks (dangling link) |
| **Cross-Filesystem** | âŒ No | âœ… Yes |
| **Directory Support** | âŒ No | âœ… Yes |
| **Link Count Impact** | Increments Target Inode Link Count | No impact on Target Link Count |
| **File Type Indicator** | Regular file (`-`) | Link file (`l`) |

---

# Linux User and Group Management

## Overview

User and group management in Linux controls system access, permissions, process isolation, and user environment setup. Accounts are divided into **Root (Superuser)**, **System/Service Accounts**, and **Regular Human Accounts**.

---

# 1. Critical User Files

### A. `/etc/passwd` (Account Metadata â€” World-Readable)
Stores user account definitions. Every user can read this file (required for tools like `ls -l` to resolve UIDs to names).

```text
username:x:UID:GID:Comment/GECOS:HomeDirectory:DefaultShell
```

- **UID 0**: `root` (Superuser privileges).
- **UID 1â€“999**: System / Service accounts (e.g., `nginx`, `sshd`).
- **UID 1000+**: Regular human accounts.
- **DefaultShell**: Program launched upon login. Use `/sbin/nologin` or `/usr/bin/false` for service accounts to block SSH/shell logins.

---

### B. `/etc/shadow` (Encrypted Passwords â€” Root Only)
Stores password hashes and expiration policies. Restricted to mode `0400` / `0000` (root only) for security.

```text
username:encrypted_hash:lastchanged:min:max:warn:inact:expire:flag
```

- **Password Hash Prefixes**:
  - `$6$` = SHA-512
  - `$y$` = Yescrypt
- **Account Locking**: A `!` or `*` at the start of the password hash field indicates the password is **locked** (cannot log in with password authentication).

---

### C. `/etc/group` & `/etc/gshadow`
- `/etc/group`: Defines groups, Primary GIDs, and lists secondary group members.
- `/etc/skel/`: Template directory containing default dotfiles (`.bashrc`, `.bash_profile`) copied to a new user's home folder during `useradd -m`.

---

# 2. Key Management Commands

### User Creation (`useradd`)
```bash
# Human User (Home dir, custom shell, primary & secondary groups)
useradd -m -s /bin/bash -g devops -G wheel,docker david

# Service Account (System user, no login shell, no home dir)
useradd -r -M -s /sbin/nologin grafana
```

| Flag | Purpose |
|---|---|
| `-m` | Create home directory (populates from `/etc/skel`) |
| `-M` | Do **NOT** create home directory |
| `-r` | Create system account (UID < 1000) |
| `-s <shell>` | Specify default login shell (`/bin/bash`, `/sbin/nologin`) |
| `-d <path>` | Specify custom home directory path |
| `-g <group>` | Set **Primary** group |
| `-G <group1,group2>` | Set **Secondary** (supplementary) groups |

---

### Modifying Users (`usermod`)
```bash
# ALWAYS USE -a WITH -G WHEN ADDING SECONDARY GROUPS!
usermod -aG secops alex   # Appends secops without wiping existing groups

# Lock & Unlock User Passwords
usermod -L alex           # Locks account (prepends ! in /etc/shadow)
usermod -U alex           # Unlocks account

# Change Shell
usermod -s /bin/bash deployer
```

> âš ï¸ **SECURITY WARNING**: Running `usermod -G secops alex` WITHOUT `-a` will **delete** `alex` from all other secondary groups! Always use `usermod -aG`.

---

### User Deletion (`userdel`)
```bash
userdel alex        # Deletes user account, keeps home directory
userdel -r alex     # Deletes user account AND removes home directory + mail spool
```

# 4. Home Directories & Manual Creation

### Purpose & Requirements:
- Holds user-specific files, SSH keys (`~/.ssh`), and shell configuration files.
- **Required for**: Human users who log in interactively.
- **Not Required for**: Background service accounts (`-M` flag).

### Manually Creating & Fixing a Home Directory:
If a user was created without a home directory (`useradd -M`) and needs one later:

```bash
# 1. Create the directory manually
sudo mkdir -p /home/david

# 2. Copy skeleton files to populate default environment
sudo cp -r /etc/skel/. /home/david/

# 3. Set proper ownership (User and Primary Group) recursively
sudo chown -R david:secops /home/david

# 4. Set secure permissions (700 or 750)
sudo chmod 700 /home/david

# 5. Update user's record in /etc/passwd
sudo usermod -d /home/david david
```

# 5. Primary vs Secondary Groups

- **Primary Group**: Set at user creation (`-g`). Stored in field 4 of `/etc/passwd`. Every file created by the user initially inherits this group.
- **Secondary (Supplementary) Groups**: Additional group memberships (`-G`). Listed in `/etc/group`. Grants permissions to extra resources (e.g. `docker`, `wheel`, `sudo`).

```bash
# Create and modify groups
sudo groupadd secops
sudo groupmod -n sec-team secops
sudo groupdel sec-team
```

# 7. `/etc/skel` (Skeleton Directory)

- **Purpose**: `/etc/skel` contains template files (default `.bashrc`, `.bash_profile`, `.bash_logout`) used to initialize a new user's environment.
- **How it works**: When `useradd -m` executes, the files inside `/etc/skel/` are automatically copied into the newly created `/home/username/` directory and ownership is assigned to that user.
- **Common Issues**: If `/etc/skel` files are corrupted, missing, or copied without hidden files (`.`), the user's shell environment will not initialize correctly.

# 8. Bash Initialization Files (Dotfiles)

When a Bash shell starts, it reads specific configuration files depending on the shell type:

### File Definitions:
- **`.bash_profile`**: Executed for **Login Shells** (e.g. logging in via SSH or console). Sets environment variables (like `PATH`, `EXPORT`) and calls `.bashrc`.
- **`.bashrc`**: Executed for **Interactive Non-Login Shells** (e.g. opening a terminal subshell inside an existing session). Contains local aliases, functions, and prompt settings.
- **`.bash_logout`**: Executed when an interactive login shell exits (used for cleanup or clearing terminal).

# 9. Bash Prompt (`PS1`) & Aliases

The Bash terminal prompt is controlled by the **`PS1`** environment variable defined inside `.bashrc` or `/etc/bashrc`.

- **Default PS1 Format**: `[\u@\h \W]\$ `
  - `\u` = Username
  - `\h` = Hostname
  - `\W` = Current working directory basename
  - `\$` = `#` for root, `$` for regular users

### Why the prompt becomes `-bash-4.2$` or `-bash-5.1$`:
This happens when `.bashrc` or `.bash_profile` is **missing** from the user's home directory. Without these files, Bash cannot set the `PS1` variable and defaults to displaying the shell name and version (`-bash-4.2$`).

### Restoring Default Prompt & Aliases:
Copy missing skeleton files back to the user's home directory, fix ownership, and source `.bashrc`:
```bash
sudo cp /etc/skel/.bash* /home/david/
sudo chown david:secops /home/david/.bash*
source ~/.bashrc
```

# 10. Troubleshooting & Security Best Practices

1. **UID 0 Security Audit Risk**: Any user account with `UID 0` in `/etc/passwd` possesses full `root` superuser privileges, regardless of its username. Never assign `UID 0` to non-root accounts.
2. **Broken Shell Prompts (`-bash-4.2$`)**: Caused by missing `.bashrc` or `.bash_profile` in the user's home directory. Copy them from `/etc/skel/`.
3. **CI/CD Deployment Accounts**: Require a valid shell (e.g. `/bin/bash`) for remote SSH command execution. Secure them using SSH key restrictions in `~/.ssh/authorized_keys` (`command="..."`).

| Symptom | Root Cause | Resolution |
|---|---|---|
| Prompt displays `-bash-4.2$` | Missing `.bashrc` or `.bash_profile` | `cp /etc/skel/.bash* /home/user/ && chown user:group /home/user/.bash*` |
| `Permission denied` on home directory | Wrong ownership or permissions | `chown -R user:group /home/user && chmod 700 /home/user` |
| SSH login fails with `Permission denied` | User shell set to `/sbin/nologin` | `usermod -s /bin/bash username` |
| User lost secondary group access | `usermod -G` ran without `-a` | `usermod -aG group1,group2 username` |
| Password authentication fails | Account is locked (`!` in `/etc/shadow`) | `usermod -U username` |

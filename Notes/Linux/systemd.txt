# Linux systemd & Service Management - Complete Beginner-to-Advanced Guide

## Overview

In modern Linux distributions (RHEL 7+, CentOS, Rocky Linux, Ubuntu 16+, Debian, Fedora), **`systemd`** is the mother of all processes. It is assigned **PID 1** by the Linux kernel during boot.

If you are new to Linux, think of `systemd` as the **Grand Supervisor**:
- It starts, stops, monitors, and restarts background services (daemons).
- It manages service startup order and dependencies at boot time.
- It captures all logs generated by running programs.
- It restarts crashed applications automatically.

---

# 1. Understanding Units and Unit Files

In `systemd`, everything it manages is called a **Unit**. Each unit has a configuration file called a **Unit File**.

### Common Unit Types:
| Unit Extension | What it represents | Real-World Example |
| :--- | :--- | :--- |
| **`.service`** | A background daemon/application | `nginx.service`, `sshd.service` |
| **`.target`** | A group of units representing a boot state | `multi-user.target` (CLI), `graphical.target` (GUI) |
| **`.timer`** | A scheduled task (the modern replacement for cron) | `logrotate.timer` |
| **`.socket`** | A network or IPC socket (starts service on demand) | `docker.socket` |
| **`.mount`** | A filesystem mount point | `tmp.mount` |

---

# 2. Where Do Unit Files Live? (Priority Hierarchy)

There are two primary locations for unit files on disk. Knowing the difference prevents accidental overrides:

| Directory | Priority | Managed By | Rule |
| :--- | :---: | :---: | :--- |
| **`/etc/systemd/system/`** | **HIGHEST** | **System Administrator** | **Put all custom services and overrides here!** |
| `/run/systemd/system/` | Medium | Runtime / Dynamic | Ephemeral units generated during runtime. |
| **`/usr/lib/systemd/system/`** | **LOWEST** | **Package Managers (`dnf`, `apt`)** | **NEVER edit files here directly!** Updates will overwrite them. |

> **Best Practice:** If you want to customize a vendor service (like `nginx.service`), never touch `/usr/lib/systemd/system/nginx.service`. Either copy it to `/etc/systemd/system/` or use `systemctl edit nginx`.

---

# 3. Anatomy of a `.service` Unit File

A `.service` file is broken down into three logical sections:

```
[Unit]     -> The Diplomat: Metadata, dependencies, ordering, rate limits
[Service]  -> The Foreman: How to launch the app, user, restart rules
[Install]  -> The Registrar: Which boot target enables this service
```

### Complete Annotated Example:

```ini
[Unit]
Description=Log Monitoring Background Service
Documentation=https://docs.example.com
# ORDERING: Start this service AFTER the network is up
After=network.target
# DEPENDENCY: Soft dependency (try to start redis, but don't fail if redis fails)
Wants=redis.service
# HARD DEPENDENCY: If postgres fails or dies, this service fails too
Requires=postgresql.service
# RATE LIMITING: If the service crashes more than 3 times within 60s, stop restarting
StartLimitBurst=3
StartLimitIntervalSec=60s

[Service]
# Type=simple: The process executed by ExecStart is the main service process
Type=simple
# SECURITY: Never run as root unless strictly required!
User=logmon
Group=logmon
# Where the process should run from
WorkingDirectory=/opt/logmon
# The EXACT command to launch the app (MUST BE AN ABSOLUTE PATH!)
ExecStart=/usr/bin/python3 /opt/logmon/monitor.py
# Command executed when running 'systemctl reload' (usually sends SIGHUP)
ExecReload=/bin/kill -HUP $MAINPID
# RESTART LOGIC: on-failure restarts if exit code != 0 or killed by signal
Restart=on-failure
# Wait 5 seconds before attempting to restart
RestartSec=5s
# Capture all stdout and stderr in the systemd journal
StandardOutput=journal
StandardError=journal

[Install]
# When 'systemctl enable' is run, create symlink inside multi-user.target.wants/
WantedBy=multi-user.target
```

---

# 4. Deep Dive: `After=` vs. `Wants=` vs. `Requires=`

This is the #1 point of confusion for beginners:

### `After=` (Ordering ONLY)
- *"Start me AFTER service X has started."*
- It does **not** create a dependency. If service X fails to start or doesn't exist, your service will still happily attempt to start!

### `Wants=` (Soft Dependency)
- *"I'd like service X to start alongside me, but I can live without it."*
- If service X fails, your service still starts and stays running.

### `Requires=` (Hard Dependency)
- *"I CANNOT survive without service X."*
- If service X fails to start, your service will NOT start.
- If service X crashes or is stopped while your service is running, `systemd` immediately stops your service too!

# 5. What Does `systemctl enable` Actually Do? (The Symlink Story)

Many beginners think `systemctl enable` starts a service. **It does not!**

### What `enable` does:
It creates a **symbolic link** in `/etc/systemd/system/<target>.wants/`:
```bash
ln -s /etc/systemd/system/logmon.service \
      /etc/systemd/system/multi-user.target.wants/logmon.service
```

When Linux boots up and reaches `multi-user.target`, `systemd` looks inside `multi-user.target.wants/` and launches every service linked there!

### The Differences:
- **`systemctl start <svc>`** : Start it right now in memory. (Will NOT start after reboot!)
- **`systemctl enable <svc>`** : Create the boot symlink. (Will start on next boot, but does NOT start right now!)
- **`systemctl enable --now <svc>`** : **Both at once!** Starts it now AND enables it for boot.
- **`systemctl disable <svc>`** : Deletes the symlink from `multi-user.target.wants/`.

# 6. What is Masking? (`systemctl mask`)

Masking is the nuclear option for stopping a service:
```bash
systemctl mask myapp
```

### How it works under the hood:
`systemd` creates a symbolic link pointing the unit file directly to **`/dev/null`**:
```bash
/etc/systemd/system/myapp.service -> /dev/null
```

### Why use it?
- When masked, a service **CANNOT be started under any circumstances** — not manually, not at boot, and not even if another service has `Requires=myapp.service`!
- To reverse it:
  ```bash
  systemctl unmask myapp
  ```

# 7. Essential `systemctl` Command Reference

```bash
# Service Control
systemctl start <service>            # Start service immediately
systemctl stop <service>             # Stop service gracefully (sends SIGTERM)
systemctl restart <service>          # Stop then Start
systemctl reload <service>           # Reload config without dropping connections (sends SIGHUP)
systemctl status <service>           # Check current state, PID, memory, recent logs

# Boot Management
systemctl enable <service>           # Enable auto-start on boot
systemctl disable <service>          # Disable auto-start on boot
systemctl enable --now <service>     # Enable and start immediately
systemctl disable --now <service>    # Disable and stop immediately

# Prevention & Safety
systemctl mask <service>             # Link to /dev/null (impossible to start)
systemctl unmask <service>           # Restore unit file

# Status Queries
systemctl is-active <service>        # Returns 'active' or 'inactive' (exit code 0 if active)
systemctl is-enabled <service>       # Returns 'enabled', 'disabled', or 'masked'
systemctl is-failed <service>        # Returns 'failed' or 'active'

# Global & Reload
systemctl daemon-reload              # MANDATORY: Tells systemd to re-read all unit files from disk!
systemctl reset-failed <service>     # Clears 'start-limit-hit' failure state so service can retry
```

# 8. Troubleshooting & Crash Diagnostics with `journalctl`

`journalctl` queries the `systemd-journald` logging service:

```bash
# Crash Debugging: Your #1 Command
journalctl -u <service> -xe          # -x adds explanations, -e jumps to end of log

# Live Stream Logs (like tail -f)
journalctl -u <service> -f

# Filter by time
journalctl -u <service> --since "15 minutes ago"
journalctl -u <service> --since "2026-10-24 10:00:00"

# Show only errors across the entire operating system
journalctl -p err -b                 # -p err: error level only, -b: current boot
```

# 9. Top Real-World Failure Scenarios & Fixes

### Failure 1: `status=203/EXEC`
* **Symptoms:** Service fails immediately on start. `journalctl` shows:
  ```text
  Process: 2436 ExecStart=/usr/local/bin/logmon (code=exited, status=203/EXEC)
  ```
* **Root Cause:** The path in `ExecStart` **does not exist**, or the file **does not have execute permissions (`+x`)**.
* **Fix:**
  1. Verify the binary path: `ls -l /usr/local/bin/logmon`
  2. If using Python/Bash scripts, ensure the interpreter is specified:
     `ExecStart=/usr/bin/python3 /opt/logmon/monitor.py`
  3. Ensure execution permission: `chmod +x /path/to/binary`

### Failure 2: `Active: failed (Result: start-limit-hit)`
* **Symptoms:** `systemctl restart myapp` refuses to start and immediately errors:
  ```text
  Failed to start myapp.service: Unit is in a failed state.
  ```
* **Root Cause:** The service crashed too many times in a short window, exceeding `StartLimitBurst`. `systemd` locked it to prevent an infinite crash loop from eating 100% CPU.
* **Fix:**
  1. Clear the failure lock:
     ```bash
     systemctl reset-failed myapp
     ```
  2. Start the service again:
     ```bash
     systemctl start myapp
     ```

### Failure 3: App works manually but crashes at boot
* **Symptoms:** Running `python3 /opt/app/main.py` works fine. Running via `systemctl` crashes with DB connection refused or missing IP.
* **Root Cause:** Missing `After=network.target` or `After=network-online.target`. The service was launched before the network interface got an IP address.
* **Fix:** Add `After=network.target` inside `[Unit]`.

### Failure 4: Forgetting `systemctl daemon-reload`
* **Symptoms:** You edited the `.service` file, but `systemctl restart` keeps running the old configuration.
* **Root Cause:** `systemd` caches unit files in memory.
* **Fix:** Always run `systemctl daemon-reload` after editing any `.service` file!

# Linux Privilege Escalation: su vs. su- vs. sudo & visudo - Complete Guide

## Overview

In Linux systems administration and DevOps, managing administrative privileges securely is vital. Granting improper root access or using the wrong switching commands can corrupt home directories, leave security audit blind spots, or lock administrators out entirely.

This guide explains the deep mechanics of **`su`**, **`su -`**, **`sudo`**, **`/etc/sudoers`**, and the drop-in architecture of **`/etc/sudoers.d/`**.

---

# 1. `su` vs. `su -` (The Core Mechanism)

Both `su` and `su -` stand for **Switch User** (or *Substitute User*). If no target username is provided, both switch to the **root** user.

In both commands, your **Effective UID becomes 0 (root)**. You have 100% full root administrative authority in both!

**So, what is the difference? The ENVIRONMENT.**

| Attribute | `su` (without dash) | `su -` (with dash) |
| :--- | :--- | :--- |
| **Shell Type** | **Non-login shell** | **Full Login shell** |
| **Current Directory (`$PWD`)** | **Stays where you were** | Changes to target user's `$HOME` (`/root`) |
| **`$HOME` Variable** | **Retains original user's `$HOME`!** | Clean root home (`/root`) |
| **`$PATH` Variable** | **Retains original user's `$PATH`** (often misses `/sbin`, `/usr/sbin`) | Clean administrative `$PATH` |
| **Shell Config Read** | Reads only non-login rc files | Reads `/etc/profile`, `/root/.bash_profile`, `/root/.bashrc` |

---

## The "Environment Pollution" Disaster (Why `su` is dangerous)

Imagine you are logged in as `azureuser`. You type `su` (no dash) to install a Python package or run an application as root:

```bash
[azureuser@server ~]$ su
Password:
[root@server azureuser]# pip install pandas
```

### What secretly happens behind the scenes:
1. `pip` checks the `$HOME` environment variable to create its cache and download directories.
2. Because you used `su` (no dash), **`$HOME` is STILL `/home/azureuser`**!
3. `pip` writes files inside `/home/azureuser/.cache/` **owned by `root:root` with permissions `700`**.
4. You type `exit` to return to `azureuser`.
5. Later, when `azureuser` runs Python, npm, or bash, they receive **`Permission Denied` inside their own home directory**!

### The `$PATH` Trap:
If you use `su` (no dash), root's administrative paths like `/usr/sbin` may not be present in your environment:
```bash
[root@server azureuser]# fdisk -l
bash: fdisk: command not found
```
Because `fdisk` lives in `/usr/sbin`, which was not loaded into your `$PATH`!

> **Golden Rule:** Whenever using `su`, **ALWAYS use `su -`** (with the hyphen). It creates a clean, isolated login shell.

---

# 2. Why Enterprises Prefer `sudo` Over `su`

In modern production environments (cloud VMs, Kubernetes nodes, enterprise clusters), direct root logins and `su` are almost universally disabled.

| Feature | `su -` | `sudo` |
| :--- | :--- | :--- |
| **Password Used** | Requires **ROOT's password** | Requires **YOUR OWN account password** |
| **Credential Sharing** | Every admin must know the root password | Nobody knows the root password; each admin has their own credentials |
| **Accountability & Auditing** | Zero audit trail. Once switched to root, all actions are anonymous. | **100% Audited.** Every command, timestamp, and user is logged to `/var/log/secure`. |
| **Granularity (Least Privilege)** | All-or-nothing (total root power). | **Fine-grained.** Can permit a developer to run ONLY `systemctl restart nginx`. |
| **Revocation** | To revoke access, you must change the root password across all servers. | Simply remove the user from the sudo group or delete their drop-in file. |

# 3. The Sudoers Configuration: `/etc/sudoers` & `visudo`

The master configuration file for sudo is:
```text
/etc/sudoers
```

### The #1 Rule of Sudoers:
> ⚠️ **NEVER edit `/etc/sudoers` directly with `vim`, `nano`, or any ordinary text editor!**
> If you make a single syntax typo, comma mistake, or indentation error and save, **`sudo` will immediately break system-wide**, locking all users out of administrative privileges!

### The Safe Way: `visudo`
Always edit sudoers using:
```bash
sudo visudo
```

**Why `visudo` is safe:**
1. **File Locking:** Prevents multiple administrators or automation scripts from editing the file at the same time.
2. **Syntax Validation:** When you save and exit (`:wq`), `visudo` parses the file in memory. If there is a syntax error, it will **REFUSE to save** and prompts you:
   ```text
   >>> /etc/sudoers: syntax error near line 42 <<<
   What now? [x=exit, e=edit, f=force]
   ```
   Pressing `e` lets you fix the typo before corrupting the live system.

# 4. Deep Dive: The Drop-In Directory `/etc/sudoers.d/`

Modern Linux distributions include this line at the bottom of `/etc/sudoers`:
```text
#includedir /etc/sudoers.d
```
*(Note: In sudoers syntax, `#includedir` is an active directive, NOT a comment).*

### Why was `/etc/sudoers.d/` created?
- **Modular Configuration:** Instead of modifying the massive, sensitive `/etc/sudoers` file, you create small, self-contained files (e.g. `/etc/sudoers.d/devops`).
- **Automation-Friendly:** Configuration management tools like Ansible, Puppet, and Cloud-Init can drop in a file without editing existing lines.
- **Clean OS Upgrades:** Prevents package update conflicts when the OS vendor updates `/etc/sudoers`.

---

## The 4 Strict Rules of `/etc/sudoers.d/`

If you violate any of these rules, `sudo` will fail or ignore your drop-in file completely:

### Rule 1: The "No Dots" Naming Rule ⚠️
Filenames in `/etc/sudoers.d/` **MUST NOT contain a period (`.`) and MUST NOT end in a tilde (`~`)**:
- ❌ `/etc/sudoers.d/developer.conf` — **COMPLETELY IGNORED by sudo!** (contains `.`)
- ❌ `/etc/sudoers.d/logmon.txt` — **COMPLETELY IGNORED by sudo!**
- ❌ `/etc/sudoers.d/admin.bak` — **COMPLETELY IGNORED by sudo!**
- ✅ `/etc/sudoers.d/developer` — **VALID & ACTIVE**
- ✅ `/etc/sudoers.d/10_logmon` — **VALID & ACTIVE**

*Why?* To prevent editor backup files (like `file.swp`, `file~`, `file.bak`) from accidentally being parsed as live privilege rules.

### Rule 2: Strict Permissions (`0440`) 🔒
Files inside `/etc/sudoers.d/` must be owned by `root:root` and have permissions **`0440`** (or `0400`):
```bash
chmod 0440 /etc/sudoers.d/my_file
chown root:root /etc/sudoers.d/my_file
```
If a file is writable by group or world (e.g. `0664` or `0777`), `sudo` considers it a security breach and **refuses to run any sudo command**:
```text
sudo: /etc/sudoers.d/my_file is world writable
sudo: no valid sudoers sources found, quitting
```

### Rule 3: Safe Editing with `visudo -f`
Never use standard `vim` to create files inside `/etc/sudoers.d/`. Use `visudo` with the **`-f`** flag:
```bash
sudo visudo -f /etc/sudoers.d/logmon
```
`visudo` will automatically validate your drop-in file and set the correct `0440` permissions upon saving!

### Rule 4: Lexicographical Ordering
Files in `/etc/sudoers.d/` are read in alphabetical (lexicographical) order:
`01-base` → `10-developers` → `99-overrides`
**Later rules override earlier rules.**

# 5. Sudoers Syntax Reference & Examples

Every rule in `/etc/sudoers` follows this syntax:

```text
WHO          WHERE = (AS_WHOM)       WHAT_COMMANDS
user/group   HOST  = (USER:GROUP)    OPTIONS: COMMAND_PATH
```

### Key Syntax Elements:
- **`username`** (no prefix) = Applies to an individual user.
- **`%groupname`** (starts with `%`) = Applies to all members of that group.
- **`ALL`** in WHERE = Any hostname/IP.
- **`(ALL)`** in AS_WHOM = Can run command as any user on the system.
- **`NOPASSWD:`** = Do not prompt for the user's password when running this command.

---

### Real-World Production Examples:

#### Example 1: Full Administrator Access (The RHEL `wheel` group)
```text
%wheel    ALL=(ALL)    ALL
```
*Meaning: Any user in the `wheel` group can run ANY command as ANY user on ANY machine (with password).*

#### Example 2: Service Restart Without Password (Least Privilege)
```text
logmon    ALL=(root)    NOPASSWD: /usr/bin/systemctl restart logmon, /usr/bin/systemctl status logmon
```
*Meaning: User `logmon` can restart and check status of `logmon` service as root without typing a password, but cannot run anything else.*

#### Example 3: Granting a Group Access to Edit Web Configs
```text
%webdev    ALL=(root)    /usr/bin/nginx -t, /usr/bin/systemctl reload nginx
```
*Meaning: Any user in `webdev` group can test and reload nginx.*

# 6. Helpful Sudo Commands for Daily Work

```bash
# Check what commands YOUR account is allowed to run with sudo:
sudo -l

# Check what commands another user can run (as root):
sudo -l -U bob

# Run a command as a different user (e.g. run a script as user 'postgres'):
sudo -u postgres psql

# View the sudo audit log on RHEL / Rocky Linux:
sudo tail -f /var/log/secure | grep sudo
```
